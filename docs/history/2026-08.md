# A contract type the backend does not guarantee is a defect class (2026-08-03)

`67e8a87` · `c783937` · `0610102` · `3e30a71` · `46599da`

## The highest-consequence bug of the day, and how it was found

`DiagnosisLine` typed its `code` prop `string` and called `code.trim()` unguarded. The backend
then started stripping an invalid comorbidity code by **deleting** the key (backend `e58b06f`),
so `d.mkb` became `undefined` — a thrown `TypeError` in the **SEALED, read-only** rendering of a
filed лист. That is the one artefact with материална доказателствена сила and no recovery path:
it cannot be edited, so a throw there is terminal.

**TypeScript did not and could not catch it.** The type was not wrong about itself; it was wrong
about the runtime. `ComorbidDiagnosis.mkb` was declared `string` while the backend deleted it.
That is a CONTRACT bug, and no compiler sees one.

It surfaced only because the task said "confirm what consumes `entry.mkb` downstream FIRST".

## Swept for the same shape (`c783937`)

Contract-first, not by grep: enumerate every key the backend can omit (`delete fields.*` /
`delete entry.*`, plus the absent-when-empty keys), then every REQUIRED-typed field in
`lib/types.ts`, then every unguarded dereference of one.

One further instance, on **both** HTML export paths: `Medication.inn` is typed required,
the backend never normalises it — every backend reader type-guards `typeof m.inn === 'string'`,
which is the authors already treating it as absent-able — and `escapeHtml(m.inn)` runs unguarded
in `generatePdfHtml` and `generateWordHtml`. `escapeHtml` dereferences immediately.

⚠ **Honest severity: this one is LATENT, not a near-miss.** Measured across 348 artifacts:
**0 of 677** medication rows lack `inn`, **0 of 259** comorbidity rows lack `diagnoza`. The type
lies; the model has never exercised the lie.

Fixed at the **choke point** — `escapeHtml` now accepts `string | null | undefined` — not at the
two call sites. The call sites are the instance; the choke point is the class, and a widening
costs nothing for defined input and cannot be forgotten by whoever adds the next export field.
Deliberately did **not** flip `Medication.inn` to optional: that ripples through `MedsPanel` and
`MedsPicker` for a hazard with zero observed instances. The residual gap (a required type the
backend does not guarantee) is a known, unobserved contract lie.

Proof it goes red: at HEAD the new suite fails 5, all on the PDF/Word paths, while
`formatPlainText` passes — it composes through `.filter(Boolean)`. That asymmetry is the bug's
signature and is now pinned.

## Allergies finally have a render surface (`3e30a71`)

`alergii` had been extracted since day one and rendered by **no** note section and **no**
exporter — the only place „Алергии" appeared in the whole product was a landing mockup depicting
a field that did not exist (see the mockup-drift entry below; that is instance three).

The амбулаторен лист has no allergy field — the НЗОК primary-document format, the НЗИС
nomenclature, and the filed листове all agree — so allergies could not become a fourth section.
Adding a field the official form does not carry to a document with материална доказателствена
сила changes what the document claims to be. They fold into **анамнеза**, through one shared
`anamnezaSectionText()` so the three exporters cannot drift.

Two rules, both pinned:
- The dictated narrative is never rewritten — the allergy line is APPENDED, never merged.
- **An empty list renders NOTHING**, never „Няма известни алергии". An empty array means nothing
  was extracted; it is not a recorded denial, and printing one asserts a clinical fact the visit
  may never have established. Same reasoning that removed the „няма открити рискове" empty state.

⚠ The correct long-term home is the НЗИС patient досие, **not** анамнеза — and that collides with
the no-patient-identity invariant. See `Cowork/NZIS-Hipokrat-Integration-Brief.md` §4b.

## The allergies chip was in the wrong review family (`46599da`)

Styled with `--color-warn`; it belongs to the AI-uncertainty family, which everywhere else uses
`--color-gold[-soft]`. The two are **byte-identical today** (`#B7791F` / `#F7EDDA`), so this
rendered zero pixels differently and no QA pass could ever have caught it — which is exactly why
it had to be fixed rather than left. The day `--color-warn` is re-tuned as a warning colour, that
chip silently leaves the uncertainty family and joins the warning family, on the allergies row,
where a warning colour makes a clinical claim the notice deliberately does not make.

Also corrected the token's own definition comment, which claimed „sole consumer is the inline
review highlight" — untrue for a while, and a comment advertising a token as low-risk to re-tune
is what makes the next instance likely.

## `mkb_correction` — the doctor sees that a code was changed (`0610102`)

Backend `ddcc3f4` repairs ICD-10-CM codes (`M17.11` → `M17.1`) and records
`{ from, to?, rule }` wherever what it FILED differs from what the model EMITTED. A silently
changed code is a claim nobody can audit later.

- `lib/types.ts` — `MkbCorrection` + `MkbCorrectionRule` (closed union).
- `lib/mkb-review.ts` — `mkbCorrectionCopy()`, the ONLY place this feature can produce
  doctor-facing text, keyed on the enum.
- `page.tsx` — `MkbCorrectionLine`, under the main diagnosis and every comorbidity row, in
  **both** the sealed and editable states, rendered as one unit with the row so a changed code
  can never appear without the sentence explaining it.

**The line this does not cross**, inherited verbatim from `field_notices`: every string states a
fact about the RECORD, never about the PATIENT. No severity, no risk word, no recommendation.
The wording lives frontend-side keyed to a closed enum, so the backend cannot widen it and the
model can never author a word of it. An **unrecognised rule renders NOTHING** rather than
guessing. Both are asserted, including a cross-repo completeness check: every rule in the
backend's `MKB_CORRECTION_RULES` must render copy.

Gold, not warn — same family correction as `46599da` above.

⚠ **Not exported to PDF/Word.** Like `uncertain_spans` and `field_notices`, this is a review aid,
and no exporter has ever carried those onto the document. Flagged as an open judgement call
rather than settled unilaterally.
⚠ **Live-browser QA owed** — `MkbCorrectionLine` is React, so `npm test` cannot exercise it.

# Mockup drift — „a depiction is a claim", generalised (2026-08-03)

Recorded as a **defect class**, not as an instance. Three instances have now been
found and each was found the same way: someone audited the render path for an
unrelated reason and noticed the marketing site was describing a different
product. None was reported by a user. None was caught by a test.

## The rule already existed — in the wrong scope

`lib/types.ts:53` has carried the sentence **„A depiction is a claim."** since the
`field_completeness` contract landed. It was written about the note's own UI: a
completeness entry may not render as `КРИТИЧНО`, because drawing something in the
shape of a clinical alert *is* making a clinical alert, whatever the data behind
it says.

The rule is correct and it was never generalised. A landing mockup is a depiction
of the product, so a landing mockup is a claim about the product — and the
landing pages were the one surface holding no one to it.

## The three instances, and why they are one class

They drift in **three different directions**, which is exactly why they read as
three unrelated bugs instead of one pattern:

| # | mockup showed | product state | mechanism | fixed by |
|---|---|---|---|---|
| 1 | a `Пациенти` nav item | the entire patient surface had been **deleted** (W3, `9eda9cb`) | product REMOVED a feature; mockup kept it | `8c92891` |
| 2 | clinical / safety capability | clinical alerts ruled **OFF** (2026-08-01 MDR) | product DISABLED a capability by ruling; mockup still claimed it | `08ef2cf`, then `f265f47` for what that sweep MISSED |
| 3 | an `Алергии` row in the note | `alergii` was extracted since day one and rendered **nowhere** — no note section, no exporter | product NEVER BUILT it; mockup showed it anyway | `4c5ae4f` (built the section; the mockup became true) |

Instance 2 is the sharpest of the three, because the *correction itself* drifted:
`f265f47` exists only to finish what `08ef2cf`'s sweep missed. A one-pass audit of
this class is not reliable.

Instance 3 is the one that should be uncomfortable. The mockup was not
aspirational marketing — `components/landing/TuberMedHeroDesktop.tsx` rendered
`<Row k="Алергии" v="няма данни" />` and a `Алергии: няма` strip, i.e. it showed
the field *populated and reassuring*, on the one field where a wrong value travels
furthest. It is true today. It was not true when it was published.

## Why nobody notices

A landing mockup is the only code in the repo with none of the usual pressures on
it:

- **no test exercises it** — it renders static strings, so it cannot fail;
- **no user reports it** — the people who would notice the discrepancy (doctors
  using the product) do not read the marketing page, and the people reading the
  marketing page have never seen the product;
- **no build gate reaches it** — `tsc`, `lint` and `build` all pass on a mockup
  that is a perfect, confident lie;
- **it is edited by a different task** than the product surface it depicts, so the
  commit that removes a feature never touches the file that advertises it.

So the failure is silent by construction, and its detection is currently
"somebody happened to look". That is the same shape as the vacuous gate the
backend collects — not a check that cannot go red, but a claim nothing checks at
all.

## The standing rule

**A change to what the product does is not complete until the mockups that depict
it have been re-read.** Adding, removing, disabling-by-flag and
never-actually-building all count: the mockup can be wrong in any direction.

Practically, when a task removes a surface, disables one behind a flag, or reveals
that a field renders nowhere, grep `components/landing/` for the thing before
closing the task. `TuberMedHeroDesktop.tsx` and `TuberMedHeroLoop.tsx` are the two
that draw a лист and are therefore the two that make field-level claims.

## Not claimed here

No sweep of the current mockups was run as part of this entry — instances 1–3 are
the ones already known. The pattern says a fourth is likely and says where to
look; it does not assert that the landing pages are correct today.
